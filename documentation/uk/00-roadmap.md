## 1. Що це і для кого

Система моніторингу (а далі — керування) невеликого тепличного господарства:
вісім теплиць на відстані 50–250 м, огірки й помідори. Кожна теплиця отримує
автономний радіовузол із датчиками; дані по LoRa стікаються на шлюз і далі на
Raspberry Pi, де бекенд зберігає виміри й шле оператору сповіщення в Telegram.

Три цілі одночасно, і їх варто тримати в голові, коли вирішуєш, що важливо:

1. **Реальне господарство.** Оператор — нетехнічний. Сповіщення простою мовою
   важливіші за дашборди.
2. **Портфоліо** для embedded / оборонного напряму: LoRa, ESP32, живлення від
   батареї, повний стек, польове розгортання.
3. **Навчання** (Python, вбудовані системи, вимірювання). Тому в репо багато
   методичних записів і чесних «не знаю, треба поміряти».

Проєкт почато 2026-07-10. На сьогодні 75 комітів, одна гілка `main`.

## 2. Загальна картина

Два незалежні тракти даних. Перший — бойовий, другий — стендовий для калібрування.

```
БОЙОВИЙ ТРАКТ (моніторинг теплиць)

  теплиця N
  ┌──────────────────────────────┐
  │ вузол Heltec V3 + SHT31 +    │  LoRa 868   ┌────────┐  USB   ┌──────────────────┐  Telegram  ┌──────────┐
  │ ємнісний датчик ґрунту       │ ──────────► │  шлюз  │ ─────► │ Raspberry Pi 5   │ ─────────► │ оператор │
  │ 18650, deep sleep 15 хв      │             │Heltec V3│        │ FastAPI + SQLite │            └──────────┘
  └──────────────────────────────┘             └────────┘        │ Telegram-бот     │  HTTP      ┌──────────┐
                                                                 │ systemd          │ ─────────► │ Expo-app │
                                                                 └──────────────────┘            └──────────┘

СТЕНДОВИЙ ТРАКТ (калібрування датчиків ґрунту)

  ┌──────────────────────────────┐  USB-serial  ┌──────────┐
  │ Heltec V3 + 4 датчики        │ ───────────► │ ноутбук  │  CSV, графіки, звіти
  │ у відрі з ґрунтом            │              └──────────┘
  │ прошивка soil-calibration    │  Wi-Fi/LTE   ┌──────────────────────┐
  │                              │ ───────────► │ Vercel + Neon        │  сторінка з телефона
  └──────────────────────────────┘              │ cloud/soil-telemetry │
                                                └──────────────────────┘
```

Логічна ієрархія в бекенді: `сервер → теплиці → вузол → сенсори`. Пороги
сповіщень живуть на рівні теплиці.

### 3.2 Прошивки (`firmware/`, PlatformIO, C++)

| Проєкт | Роль | Стан |
|---|---|---|
| `gateway/` | LoRa → USB-serial на Pi, додає RSSI/SNR, OLED | ✅ у бою на Pi, прошивається з Pi по SSH (`make deploy-gateway`) |
| `greenhouse-node-lowpower/` | **бойовий вузол**: прокинувся → Vext → датчики → LoRa JSON → deep sleep | 🔧 працює; потрібне перепідключення живлення датчика (3V3 → `Ve`), щоб числа трималися; 7 збірок для експериментів зі сном |
| `greenhouse-node/` | стендовий вузол: 1 Гц, OLED, Serial, без сну | ✅ лише як **опорний** для етапу 3 (порівняння зі сном) |
| `soil-calibration/` | стенд: 4 датчики у відрі, CSV raw+мВ по USB, команди доливу, Wi-Fi у хмару | 🔧 активний експеримент; 11 Python-інструментів; незакомічені правки (фаза 0 Wi-Fi) |
| `node_sensor/` | — | ⚠️ порожня папка, але згадана в `structure.md`, README, docker-compose |

Наскрізні рішення: Serial вимкнено в бойовій прошивці; події заліза (brownout,
watchdog, ресети) їдуть 64-байтним бітмаском із RTC-пам'яті в пакеті; Docker
для збірки, `pio` на хості лише для заливки.

1. Датчик у вузлі фізично v1.2, рішення — v2.0; жодна константа прошивки ще не перемкнута.

**Дослідження як timeline.** `research/index.md` — одна сторінка-стрічка:
дата → назва етапу → картинка (фото стенду або графік) → висновок одним
рядком → посилання на повну сторінку етапу. Сирий лог (`docs/дослідження/калібрування-ґрунту.md`,
843 рядки) лишається де є; у `research/` переносяться лише методика, ключові
числа й висновки. Картинки, які вже є: `calibration_curve.png`, `settle_curve.png`,
`schema.jpg` — решту (фото відра, плат, клемників) треба зробити.

**Гайди.** Кожен гайд — одна задача, один шлях, перевірений руками: передумови →
кроки → як зрозуміти, що вийшло → типові пастки. Перший — калібрувальний стенд,
бо для нього вже є прошивка, 11 інструментів і набита шишками процедура.

**Сайт.** Усе вище — звичайний Markdown, тому сайт будується поверх без
переробки. Рекомендація: **MkDocs Material** — Python (збігається з навчальною
ціллю), двомовність через `mkdocs-static-i18n`, пошук, темна тема, деплой на
GitHub Pages одним workflow. Timeline робиться заголовками з датами + картинка
+ блок-висновок, без окремих плагінів; відео — `<iframe>` YouTube прямо в MD.
Сайт — після того, як наповнимо `uk/` хоча б довідником і першим гайдом;
спочатку зміст, потім обгортка.

Правила, щоб лишатись послідовними:

- **Одне джерело правди на факт.** Пінаут — лише в `03-hardware.md`, решта посилається.
- **Довідник ≠ лог ≠ дослідження.** Сирі логи лишаються в `docs/`, висновки — у `research/`, поточний стан — у довіднику.
- **Спочатку українська, переклад після затвердження** розділу, не паралельно.
- Стан компонента позначається тією ж легендою, що вгорі цього файлу.
