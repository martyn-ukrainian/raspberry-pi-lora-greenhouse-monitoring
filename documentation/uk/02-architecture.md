# Архітектура

## Три шари

| Шар | Де | Що робить |
|---|---|---|
| **Вузол** | у кожній теплиці | прокидається, вмикає датчики, міряє, шле один LoRa-пакет, засинає |
| **Шлюз** | розсадна теплиця (хаб) | слухає LoRa, додає RSSI/SNR, віддає рядок JSON по USB |
| **Сервер** | Raspberry Pi 5 поруч зі шлюзом | зберігає, рахує пороги, шле Telegram, віддає API застосунку |

Топологія — **зірка**: всі вузли шлють на один шлюз, без LoRaWAN і без мережевого
сервера. Власна адресація `node_id`. Для 6–14 вузлів цього достатньо; перевага —
жодної зовнішньої інфраструктури й повний контроль над форматом.

## Бойовий тракт: від датчика до оператора

```
 вузол (Heltec V3)                      шлюз (Heltec V3)            Raspberry Pi 5
 ┌────────────────────────┐             ┌──────────────┐            ┌──────────────────────────────┐
 │ deep sleep 15 хв       │             │ startReceive │            │ usb_adapter.py               │
 │  ↓ прокинувся          │  LoRa 868   │  ↓ пакет     │  USB/NDJSON│  ↓ node_id → мітка (nodes.yaml)
 │ Ve on → SHT31, ґрунт,  │ ──────────► │ + rssi, snr  │ ─────────► │  ↓ err-біти → POST /events   │
 │ vbat → JSON → transmit │             │ → Serial     │            │  ↓ POST /measurements        │
 │  ↓ Ve off → sleep      │             └──────────────┘            │ main.py                      │
 └────────────────────────┘                                         │  ↓ SQLite                    │
                                                                    │  ↓ пороги dwell/cooldown     │
                                                                    │  ↓ Telegram sendMessage ─────┼──► оператор
                                                                    │  ↔ HTTP API ─────────────────┼──► застосунок
                                                                    └──────────────────────────────┘
```

### Пакет вузла

Один JSON-рядок, поля у фіксованому порядку:

```json
{"type":"measurement","node_id":0,"air_temperature":27.4,"air_humidity":71.2,
 "soil_moisture":43,"vbat":3.87,"boot":412,"err":68,"eseq":9}
```

| Поле | Хто ставить | Примітка |
|---|---|---|
| `node_id` | вузол | число; мапиться в мітку (`greenhouse-1`…) на сервері |
| `air_temperature`, `air_humidity` | вузол | **відсутні**, якщо SHT31 не відповів (3 спроби) — відсутність ≠ нуль |
| `soil_moisture` | вузол | 0–100, зараз лінійний `map()` — тимчасово, до калібрування |
| `vbat` | вузол | В, через дільник ×4.9 |
| `boot` | вузол | лічильник пробуджень з RTC-пам'яті; скинувся в 1 — був не таймерний ресет |
| `err`, `eseq` | вузол | бітмаска подій заліза + порядковий номер; є лише коли щось сталося; гаситься після успішної передачі |
| `rssi`, `snr` | шлюз | дописує перед `}` |

Стендовий вузол (`greenhouse-node`) шле те саме, але з `uptime` замість `boot`
і при відмові SHT31 ставить нулі (стара поведінка; у бойовому — поле прибирається).

Шлюз окремо шле власні події: `{"type":"event","node_id":255,"code":N,"detail":N}`.

### Параметри радіо

У коді задана **лише частота** `868.0` МГц. Spreading factor, смуга, coding
rate, sync word, потужність — дефолти RadioLib для SX1262 (SF9, 125 кГц, 4/7,
0x12, 10 dBm). Це не налаштовано явно — коли дійдемо до дальності/батареї,
стане окремим рішенням.

Шлюз приймає **неблокуюче** (`startReceive` + переривання DIO1): блокуючий
`receive()` рвав пакети довші за кілька десятків байт.

### Події заліза замість логів

Вузол не пише логів — нема куди й нема кому читати. Замість цього в RTC-пам'яті
(переживає deep sleep) лежить 64-байтний слот: лічильник пробуджень, бітмаска
помилок, кільце з 24 останніх подій. Бітмаска їде в пакеті полем `err`, адаптер
розкладає її на окремі записи `/events`. Коди — у [04-firmware.md](04-firmware.md#події-заліза).

### Ієрархія в сервері

```
agro-server
└── greenhouses/                  (config/thresholds.yaml)
    └── greenhouse-1  "Помідори 2 пльонки"   ← node_id 0
        └── вузол
            ├── SHT31        → air_temperature, air_humidity
            └── ємнісний     → soil_moisture
```

Пороги й `dwell` — на рівні теплиця × датчик; `cooldown` — глобальний.

## Стендовий тракт: калібрування

Окрема плата з прошивкою `soil-calibration`, до чотирьох датчиків у відрі:

```
 Heltec V3 + 4 датчики + SHT31 ──USB──► ноутбук: CSV (опорний тракт, ніколи не вимикається)
                                ──Wi-Fi──► хотспот телефона ──LTE──► Vercel (FastAPI) + Neon (Postgres)
                                                                      └─► сторінка з телефона, «влив N мл», CSV
```

LoRa тут не бере участі. Wi-Fi-гілка існує, щоб знімати калібрування в теплиці
без ноутбука. Побоювання, що імпульси передачі просаджують шину ADC, перевірено
фазою 0 (2026-08-23): шум росте лише на 18–30 % — радіо можна не ховати. Контракт пачок — `docs/INGEST-CONTRACT.md`,
деталі — [07-cloud-telemetry.md](07-cloud-telemetry.md).

## Моделі розгортання

**Self-hosted (є зараз).** Оператор ставить сервер на свій Pi, створює свого
бота через @BotFather, дані лишаються в нього.

**Спільний hub (задум).** Один Telegram-бот на багато ізольованих інстансів;
hub маршрутизує повідомлення за per-user токеном. У коді цього немає — є лише
протокол `Notifier`, через який такий канал можна додати без правки логіки
алертів. `NOTIFIER=telegram_hub` з README поки не існує як змінна.

## Що заплановано в архітектурі, але не реалізовано

З `docs/greenhouse_architecture.md` (дизайн, не код):

- **Двосторонній протокол**: база → вузол команда-ціль
  (`{"cmd":"polyv","target_soil":60,"max_sec":600}`), вузол → база рапорт
  `done`/`alarm`; `msg_id` + ACK для ідемпотентності; timestamp ставить база
  (у вузла нема RTC-годинника).
- **Локальна логіка поливу на вузлі** із запобіжниками — вузол лишається
  автономним, коли база мовчить.
- Бінарний формат пакета замість JSON, HMAC/CRC із сіллю.
- Живлення дальніх вузлів від сонячної панелі + LiFePO4.
