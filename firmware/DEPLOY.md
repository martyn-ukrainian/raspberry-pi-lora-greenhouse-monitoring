# Деплой gateway-прошивки на Raspberry Pi

> **2026-08-24. USB-тракт непрацездатний фізично.** Шнур, яким шлюз
> під'єднаний до малини, виявився зарядним: ліній даних у ньому нема, тому
> `lsusb` на Pi порожній, хоча плата живиться нормально. Робочий шлях тепер —
> **мережевий режим** (розділ у кінці файла): шлюз дублює свій NDJSON-потік у
> TCP, а адаптер на Pi читає його з сокета замість порту. Заливка при цьому
> йде з Mac, бо `make deploy-gateway` нижче теж вимагає ліній даних.
> Розділ про USB лишається — він знову стане актуальним, щойно знайдеться
> нормальний кабель.

`gateway` фізично сидить на USB Raspberry Pi (`/dev/ttyUSB0`) поруч з базою —
кабель до Mac туди не дотягнеться. Замість того щоб щоразу нести плату на
стіл, збірка й заливка йдуть **прямо на Pi**: команда запускається з Mac,
уся робота (rsync коду, збірка, `esptool upload`) виконується на Pi через SSH.

`node` так не заллєш — він з'єднаний тільки по LoRa, не на USB Pi.
Для нього й далі `make upload PROJECT=greenhouse-node` з Mac, плата на столі.

## Одноразове налаштування на Pi

```
ssh agro@agro-pi.local '~/.local/bin/uv tool install platformio'
```

(`uv` вже стоїть на Pi під `~/.local/bin/uv` — не в PATH неінтерактивного
SSH-сеансу, тому виклики нижче йдуть повним шляхом.)

## Заливка

```
cd firmware
make deploy-gateway
```

Що відбувається:
1. `rsync` копіює `firmware/gateway/` на Pi (без `.pio` — кеш збірки лишається
   на Pi, наступні заливки швидші за першу).
2. SSH-сесія на Pi: `systemctl stop agro-adapter` (звільняє `/dev/ttyUSB0`),
   потім `pio run -t upload`, і **завжди** `systemctl start agro-adapter`
   в кінці — навіть якщо заливка впала (`trap ... EXIT`).

Змінні (перевизначай при потребі):

| Змінна | Дефолт | Навіщо |
|---|---|---|
| `PI_HOST` | `agro@agro-pi.local` | SSH-адреса Pi |
| `PI_DIR` | `agro` | шлях до репо на Pi |
| `PI_GATEWAY_PORT` | `/dev/ttyUSB0` | порт, на якому сидить gateway |

## Критична деталь

`/dev/ttyUSB0` не можна тримати вдвох — `agro-adapter` читає з нього
телеметрію постійно. Заливка **обов'язково** зупиняє сервіс перед `upload`
і піднімає назад після — незалежно від успіху заливки. Якщо runнути `pio
upload` на Pi вручну, без зупинки сервісу — заливка з високою ймовірністю
провалиться (порт зайнятий), як не раз траплялось локально з `pio device
monitor`.

## Ризики

- **Авто-reset у bootloader.** Heltec V3 (CP210x) підтримує DTR/RTS-авто-reset,
  `esptool` зазвичай сам заганяє плату в режим прошивки. Якщо ні (плата не
  відповідає) — треба фізично затиснути кнопку `BOOT` на платі. Якщо поруч
  з Pi нікого нема — деплой краще робити, коли є хтось на місці "про всяк
  випадок", хоча б перший раз.
- **Перший білд повільний** — тягне тулчейн `espressif32` (кілька сотень МБ),
  разово. Далі йде з кешу на Pi, швидко.
- Телеметрія переривається на час заливки (зазвичай до хвилини) — `lastSeen`
  вузлів на клієнті/OLED під час цього стрибне.


## Мережевий режим: шлюз віддає дані по Wi-Fi

Потрібен, коли USB-тракт недоступний (зарядний шнур) або коли шлюз зручніше
поставити не там, куди дотягується кабель від малини.

Змінюється **тільки джерело байтів**. Формат потоку той самий NDJSON, розбір,
мапінг номерів у мітки (`config/nodes.yaml`) і розкладання бітмаска `err`
лишаються в `usb_adapter.py`: переносити їх у C++ означало б тримати дві
реалізації одного контракту.

### Що на платі

`firmware/gateway`, середовище `wifi_pi`. Увесь вивід шлюза йде через одну
функцію `emitLine()`, і мережа — просто її другий отримувач; Serial при цьому
працює як раніше, тож із нормальним кабелем видно той самий потік.

Поки сокета нема, рядки лягають у чергу на 24 позиції. При переповненні
витісняється найстаріше, а після відновлення зв'язку першим іде
`GWEV_SINK_DROP` зі скільки саме втрачено — інакше провал у даних на сервері
виглядав би як тиша в ефірі, тобто як несправність вузла.

Адреса приймача за замовчуванням `agro-pi.local:9009`. Саме ім'я, а не IP:
адреса малини вже їздила по DHCP (`.88` → `.104`), і кожен переїзд означав би
перепрошивку. Ім'я в домені `.local` розв'язується через mDNS; якщо в мережі
його нема, підставити літерал адреси через `SINK_HOST` у `firmware/.env`.

```
cd firmware
make upload PROJECT=gateway PIO_ENV=wifi_pi SERIAL_PORT=/dev/cu.usbserial-0001
```

`WIFI_SSID` і `WIFI_PASS` беруться з `firmware/.env` — Makefile підставляє їх
будь-якому середовищу з префіксом `wifi_`. **Мережа має бути та сама, в якій
живе малина**, інакше плата підключиться, але сервера не побачить.

### Що на Pi

```
# server/.env
GATEWAY_SOURCE=tcp
GATEWAY_TCP_PORT=9009
```

Unit `agro-adapter.service` більше **не** прив'язаний до `dev-ttyUSB0.device`:
у мережевому режимі такого пристрою не існує, і зі старим `BindsTo=` сервіс не
стартував би ніколи. Копія попереднього варіанту лежить поруч як
`agro-adapter.service.usb-backup`.

### Перевірка

```
ssh agro@agro-pi.local 'ss -ltn | grep 9009'                    # слухає?
ssh agro@agro-pi.local 'ss -tn "( sport = :9009 )"'              # плата підключилась?
ssh agro@agro-pi.local 'grep -E "Gateway|Forwarded" ~/agro/server/logs/agro.log | tail'
```

Приймальний бік можна перевірити без плати — надіславши в сокет рядок руками:

```
python3 -c 'import socket,json; s=socket.create_connection(("agro-pi.local",9009)); \
  s.sendall((json.dumps({"type":"measurement","node_id":1,"air_temperature":20.0, \
  "air_humidity":40.0,"soil_moisture":50,"rssi":-70,"snr":9.0})+"\n").encode())'
```

На екрані шлюза стан каналу показує правий верхній кут: `net` — сокет живий,
`net?` — Wi-Fi є, сервера нема, `wifi?` — нема мережі.
