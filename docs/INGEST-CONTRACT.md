# Контракт `/api/ingest` — що шле плата

Прошивка: `firmware/soil-calibration`, середовище `wifi_field`.
Пише **той самий** потік, що йде в USB-CSV — навмисно: два тракти мають бути
зіставні поле в поле, інакше їх не звірити.

## Запит

```
POST <INGEST_URL>
Content-Type: application/json
Authorization: Bearer <INGEST_TOKEN>      # якщо токен непорожній
```

Тіло — одна пачка на 30 замірів (≈30 с при періоді 1 с):

```json
{
  "device": "441bf6fb8aac",
  "seq": 12,
  "labels": ["v20a", "v20b", "ch4", "ch5"],
  "samples": [
    {
      "t": 1234.5,
      "water_ml": 70.0,
      "event": "water+50.0",
      "raw": [2874, 1189, 660, 117],
      "mv":  [2409, 1018, 566, 95],
      "air_t": 24.10,
      "air_h": 52.00
    }
  ]
}
```

## Поля

| Поле | Тип | Що це |
|---|---|---|
| `device` | string | MAC плати без роздільників — стабільний ID між перезапусками |
| `seq` | int | номер пачки від старту плати; **не унікальний глобально** |
| `labels` | string[] | імена каналів; порядок збігається з `raw` і `mv` |
| `samples[].t` | float | секунди від початку прогону (не UNIX-час) |
| `samples[].water_ml` | float | влита вода, **наростаючим підсумком** |
| `samples[].event` | string | **необов'язкове**, лише коли щось сталось |
| `samples[].raw` | int[] | сире 12-бітне ADC, 0..4095 |
| `samples[].mv` | int[] | те саме в мілівольтах |
| `samples[].air_t/air_h` | float | **необов'язкові** — SHT31 |
| `samples[].vbat` | float | **необов'язкове** — напруга батареї, В |
| `samples[].bat_pct` | int | **необов'язкове** — груба оцінка залишку, 0–100 |

## Три речі, які легко зробити неправильно

**0. `vbat`/`bat_pct` є лише на батареї.** На USB дільник читає ~0, і плата
навмисно **не надсилає** ці поля: «не знаємо» це не «розряджено вщент». Не
малюй 0% там, де їх просто нема.

`bat_pct` рахується по таблиці типової кривої 18650, не лінійно від напруги —
Li-ion віддає першу третину ємності від 4,2 до 3,7 В, а решту дві від 3,7 до
3,4. Точність ±10%: годиться для «скільки ще протримає», не для обліку енергії.

**1. Відсутнє поле ≠ нуль.** `air_t`, `air_h` і `event` **не надсилаються**,
коли даних немає. Це свідоме рішення прошивки: «не знаємо» і «нуль градусів»
різні речі, і вигаданий нуль поїхав би в базу як справжній замір. Не
підставляй за них значення за замовчуванням.

**2. `t` — не час доби.** Це секунди від старту прогону, і команда `r` на
платі **скидає їх у нуль**. Мітку реального часу став на приймальному боці,
за моментом POST.

**3. Пачки приходять повторно.** При обриві мережі плата ставить пачку в чергу
й надсилає пізніше — разом із боргом, **перед** свіжою. Тобто порядок `seq`
**не гарантований монотонним** у часі приходу, і одна пачка може прийти
**двічі**, якщо відповідь загубилась після запису.

Дедуплікуй за `(device, seq)`. Черга тримає 4 пачки; при переповненні
викидається найстаріша, і в даних буде розрив.

## Режими радіо

За замовчуванням (`wifi_field`) радіо **вимкнене під час заміру** і вмикається
лише на відправку. Це рознесення в часі захищає ADC від просадки живлення при
передачі — наш шум σ = 0,6 мВ, і саме він дає роздільність 0,15 мл води.

Наслідок для приймача: **між пачками бувають розриви в `t`** на 1–3 секунди
(переконнект). Це нормально, не втрата.

`wifi_field_always` тримає радіо піднятим — існує лише для порівняння шуму.

## Відповідь сервера

```json
{"ok": true, "dup": false, "pour_ml": 50.0}
```

- `dup: true` — така `(device, seq)` уже була; записів не додано, але це
  **2xx**: плата має прибрати пачку з черги, а не слати знову.
- `pour_ml` — **необов'язкове**: є недоставлений долив, натиснутий на сторінці.
  Плата має застосувати його як команду `w N` (вода += N, подія `water+N.0` у
  наступному замірі). Сервер повертатиме той самий `pour_ml` на кожен POST,
  доки не побачить подію `water+N` у даних — тож загублена відповідь долив
  не губить, а плата **не має** застосовувати одне й те саме значення двічі
  поспіль без події між ними. Сьогоднішня прошивка відповідь не читає —
  крок 1b.4 у `план-wifi-реалізація.md`.

Реалізація: `cloud/soil-telemetry/main.py`.

## Що корисно віддавати назад

Для сторінки треба:

- останні N замірів по `device`;
- **σ за останню хвилину на канал** — жива перевірка, що канал живий, а не
  показує правдоподібне сміття. Ми вже тричі ловили стабільні числа, які
  нічого не означали;
- **кнопку «влив N мл»** — вона має долітати до плати або записуватись поруч
  із даними: це єдина ланка, де вже губились дані;
- експорт CSV з тими самими колонками, що в `serial_tee`.

## Порядок величин

| | |
|---|---|
| Пачка | ≈5–6 КБ JSON |
| Частота | 1 пачка / 30 с на пристрій |
| Прогін 1–2 год | 120–240 пачок ≈ 7 200 замірів |

Навантаження мізерне — сховище обирати за простотою підняття, не за
масштабованістю.
