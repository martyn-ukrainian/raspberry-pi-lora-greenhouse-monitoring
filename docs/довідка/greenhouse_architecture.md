# Технічна архітектура: система розумного поливу теплиць

> Розподілена система моніторингу й автоматичного поливу на базі LoRa + ESP32,
> з централізованим "мозком" на базовій станції та автономними вузлами в теплицях.
> Задум: спершу надійна автоматика на порогах, згодом — ML-шар для прогнозного керування.

---

## 1. Загальний принцип

Система побудована за моделлю **supervisory control** (наглядове керування):

- **База (мозок)** ставить *цілі* — "доведи вологість до 60%".
- **Вузол теплиці** *виконує* й **сам замикає контур** — ллє, міряє, зупиняється по досягненні цілі.

Ключове правило: **вода ніколи не залежить від радіозв'язку.** Рішення "коли зупинити полив"
живе локально, у тому ж вузлі, що керує клапаном. Зв'язок може обірватись відразу після команди —
вузол однаково доведе полив до цілі й безпечно закриється.

```
┌─────────────────────┐        LoRa P2P        ┌──────────────────────────┐
│   БАЗА (мозок)      │  ◄── дані про стан ──   │  ВУЗОЛ ТЕПЛИЦІ           │
│   ESP32/RPi + LoRa  │                         │  ESP32 + LoRa + сенсори  │
│                     │  ── команда-ціль ──►    │  + реле + клапан         │
│ • збирає дані       │                         │                          │
│ • вирішує ціль      │  ◄── рапорт ────────    │ • міряє вологість/темп   │
│ • логує / вчиться   │                         │ • ллє воду локально      │
│ • НЕ слідкує за     │                         │ • САМ вирішує коли стоп  │
│   процесом поливу   │                         │ • запобіжники на місці   │
└─────────────────────┘                         └──────────────────────────┘
                                                 (× N теплиць)
```

---

## 2. Розподіл обов'язків

| База (мозок) | Вузол теплиці (edge) |
|---|---|
| Збирає дані з усіх теплиць | Міряє свою вологість / температуру |
| Тягне зовнішній прогноз (API) | Виконує полив |
| Вирішує **ціль**: "до 60%" | Вирішує **коли стоп**: досяг цілі |
| Кинув команду й пішов далі | Сам замикає контур зворотного зв'язку |
| Логує все в базу даних | Тримає локальні запобіжники |
| Пізніше — ML-прогноз і корекція | Рапортує результат назад |

Мозок **не блокується** очікуванням: одна команда — і він вільний обслуговувати решту теплиць.
Це те, що дозволяє масштабувати систему на будь-яку кількість теплиць.

---

## 3. Топологія зв'язку

**Технологія: чиста LoRa point-to-point (P2P), НЕ LoRaWAN.**

- LoRa P2P — двосторонній обмін коли завгодно, власний простий протокол, повний контроль.
  Ідеально для масштабу "кілька теплиць + одна база".
- LoRaWAN — надлишковий: потребує шлюзу й сервера, а прийом на кінцевому вузлі обмежений
  часовими вікнами. Для цього проєкту не потрібен.

**Обмеження LoRa, які треба тримати в голові:**
- Повільна, малий об'єм даних (плата за дальність).
- Годиться для "раз на хвилину скинути показники" й "прийняти коротку команду" — це байти.
- НЕ для потоку: жодного відео чи щосекундних замірів через LoRa.
- Контур реального часу (полив ↔ вимір) живе **локально** у вузлі, а не ганяється через радіо.

## 4. Апаратна схема вузла теплиці

```
                    ┌──────────────────────────────────────┐
                    │            ВУЗОЛ ТЕПЛИЦІ               │
                    │                                        │
   [Сенсор          │   ESP32                                │
    вологості] ─────┼──► GPIO (ADC)                          │
                    │      │                                 │
   [Сенсор          │      ├──► GPIO (ADC/1-Wire)  ◄─────────┼─ [DHT/темп/вологість повітря]
    ґрунту] ────────┼──► GPIO                                │
                    │      │                                 │
   [LoRa SX1276/    │      ├──► SPI ◄──────────────────────► [антена]
    RA-02] ─────────┼──►                                     │
                    │      │                                 │
                    │      └──► GPIO ──► [Релейний модуль] ──┼──► [Клапан 12В NC]
                    │                    (оптрозв'язка)       │
                    └──────────────────────────────────────┘
                              │                    │
                     [Живлення ESP32]      [Окреме живлення 12В]
                        (3.3/5В)              (клапан/помпа)
                              └────── спільна GND ──────┘
```

### Компоненти вузла
- **ESP32** — контролер вузла (Wi-Fi не обов'язковий, але корисний для налагодження).
- **LoRa-модуль** — SX1276 / RA-02 / Ra-01 (433 або 868 МГц залежно від регіону й антен).
- **Сенсори** — вологість ґрунту (вже замовлені), температура/вологість повітря (DHT22 / BME280).

**⚠️ Перевір тип замовлених сенсорів вологості ґрунту:**
- **Резистивні** (два голі металеві щупи) — кородують у вологому ґрунті за тижні-місяці,
  показники пливуть, потім вмирають. Для системи, що *керує водою* за їхніми показами — небезпечно.
- **Ємнісні (capacitive)** — без відкритого металу в ґрунті, живуть роками. Для цієї системи — тільки вони.
- Якщо замовлені резистивні — використай їх для прототипування на столі, а в теплицю докупи ємнісні.

**Одна точка виміру ≠ стан теплиці.** Один сенсор міряє 10 см ґрунту навколо себе, а не грядку.
Мінімум для рішень про воду — **2-3 сенсори на зону, рішення за медіаною**. Це ще й безкоштовна
діагностика: якщо один сенсор різко розійшовся з двома іншими — він і є зламаний (санітарка з п.6
отримує еталон для порівняння).
- **Релейний модуль** — 1 канал з оптронною розв'язкою (захищає ESP32). Для старту — саме реле,
  MOSFET пізніше (тихіший, довговічніший, бо реле механічно зношується).
- **Клапан 12В NC** (normally closed) — при відкритому відводі під тиском від магістралі.

## 5. Схема водопостачання

**Поточна конфігурація (як з'ясовано):**
- Вода набирається в басейн.
- Насос жене воду по всіх теплицях; імовірно вже стоїть **реле тиску**.

**Цільова схема — "розділення відповідальності":**

```
[Басейн] ─► [Насос + реле тиску] ─► [Магістраль під тиском] ─┬─► [Теплиця 1: клапан 12В]
                                                              ├─► [Теплиця 2: клапан 12В]
    Насос відповідає ЗА ТИСК                                  └─► [Теплиця N: клапан 12В]
    (власна автоматика,                                            ESP32 відповідає
     ESP32 його не чіпає)                                          ЗА "полити свою теплицю"
```

- **Насос тримає тиск** у магістралі через власне реле тиску / гідроакумулятор — жива своя автоматика.
- **Кожна теплиця** просто відкриває **свій** клапан, коли треба. Вода вже під тиском — пішла самопливом тиску.
- Немає боротьби за насос між теплицями, немає координації, кожен вузол автономний.

**Чому клапан, а не керування насосом з ESP32:** якщо ESP32 керуватиме насосом напряму, кілька теплиць
почнуть конфліктувати за один насос. Клапан на кожному відводі знімає цю проблему повністю.

## 6. Логіка поливу (закритий контур на вузлі)

Мозок дає **ціль**, вузол виконує й **сам** вирішує коли зупинити. Мозок далі не слідкує.

**⚠️ Важлива фізична поправка: полив має бути ІМПУЛЬСНИМ, не безперервним.**
Вода не миттєво доходить до глибини сенсора — їй треба хвилини, щоб всотатись. Якщо лити
безперервно й міряти щосекунди, сенсор "не бачить" воду, яка вже в ґрунті, і система переливає
(overshoot). Правильний цикл: **лий короткий імпульс → закрий → чекай всотування → заміряй → повтори.**

```cpp
// Вузол теплиці отримав команду: "лий до вологості 60%"

void polyv(int cil_vologist) {
    unsigned long start = millis();
    int cykliv = 0;

    while (chytaty_vologist() < cil_vologist) {

        // ── ЗАПОБІЖНИК 1: таймаут на всю операцію ──
        if (millis() - start > MAX_CHAS_POLYVU) {       // напр. 30 хв разом із паузами
            rapport_bazi("AVARIA: taimaut, vologist ne roste");
            return;                                     // рятує від потопу при поломці сенсора
        }

        // ── ЗАПОБІЖНИК 2: ліміт циклів ──
        if (++cykliv > MAX_CYKLIV) {                    // напр. 10 імпульсів
            rapport_bazi("AVARIA: bagato cykliv, sensor ne reaguye");
            return;
        }

        // ── ЗАПОБІЖНИК 3: санітарка сенсора ──
        if (!vologist_validna()) {                      // стрибок 30→90% за сек, або >100%
            rapport_bazi("AVARIA: pidozrilyi sensor");
            return;
        }

        // ── Імпульс поливу ──
        vidkryty_klapan();
        delay(IMPULS_SEK * 1000);                       // напр. 30 сек лиття
        zakryty_klapan();                               // клапан ЗАКРИТИЙ під час паузи!

        delay(PAUZA_VSOTUVANNYA * 1000);                // напр. 2-3 хв — вода доходить до сенсора
    }

    rapport_bazi("GOTOVO: vologist=X, cykliv=N, lyv sumarno Y sek");  // ← золото для ML
}
```

Бонус імпульсного підходу: клапан закритий більшу частину часу операції, тож навіть
залипання реле в одному циклі обмежене одним імпульсом, а не всім поливом.

### Обов'язкові запобіжники (без них система одного дня заллє теплицю)
1. **Таймаут.** "Лий поки не ціль **АБО** поки не мине N хвилин — що раніше." Ловить зламаний сенсор,
   що вічно показує «сухо».
2. **Ліміт циклів.** Максимум N імпульсів на одну команду — друга лінія захисту від "сенсор не реагує".
3. **Санітарна перевірка сенсора.** Нереальний стрибок або значення поза діапазоном → не вір, стоп.
4. **Клапан NC (normally closed).** Пропало живлення — вода перекрилась сама. Теплицю не заллє.
5. **Апаратний watchdog ESP32.** Якщо прошивка зависла з відкритим клапаном — watchdog перезавантажує
   контролер, а після ребуту клапан за замовчуванням закритий (NC + GPIO у LOW при старті).

## 7. Протокол обміну по LoRa

Короткі повідомлення (байти), власний простий формат. Приклад набору:

### Вузол → База (телеметрія, періодично)
```json
{ "id": "gh_1", "t": 28.4, "hum_air": 55, "hum_soil": 32, "valve": 0, "ts": 17200 }
```

### База → Вузол (команда-ціль)
```json
{ "cmd": "polyv", "target_soil": 60, "max_sec": 600 }
```

### Вузол → База (рапорт про результат)
```json
{ "id": "gh_1", "event": "done", "soil_after": 60, "watered_sec": 90 }
{ "id": "gh_1", "event": "alarm", "reason": "timeout" }
```

Рапорти "лив 90 сек → вологість піднялась на 28%" накопичуються на базі й стають
навчальними даними: "скільки води за яких умов дає який ефект".

### Надійність протоколу (слабке місце наївної версії — закриваємо одразу)

Радіо губить пакети. Команда "полий" може не дійти, а рапорт "полив" — загубитись,
і база подумає, що полив не відбувся, і надішле команду ще раз → подвійний полив.

- **msg_id у кожному повідомленні.** Вузол пам'ятає останній оброблений id: повторна команда
  з тим самим id ігнорується (ідемпотентність). База може безпечно ретраїти.
- **ACK на команду.** Вузол відповідає "прийняв cmd #42" одразу, ще до виконання.
  Немає ACK за N секунд → база повторює ту саму команду (той самий id).
- **Часу на вузлі немає.** У вузла нема RTC — поле `ts` не має сенсу слати з вузла.
  **База ставить timestamp у момент отримання.** Вузол шле тільки відносні величини (uptime, тривалості).
- **JSON — тільки для старту.** Для налагодження зручно, але для LoRa марнотратно (кожен байт = час
  в ефірі). Коли запрацює — перейти на компактний бінарний формат (struct, ~10-15 байт на пакет).
- **Мінімальний захист.** LoRa — відкритий ефір: будь-хто з модулем може надіслати "polyv".
  Мінімум — спільний секрет + перевірка (простий HMAC/CRC із сіллю). Не криптографія рівня банку,
  але випадковий чужий пристрій чи сусідський експеримент команду не підробить.

## 8. Живлення й безпека (де новачки заливають теплицю — буквально)

- **Роздільне живлення.** Клапан/помпа НЕ живляться від ESP32. Окремий блок 12В.
  Спільна тільки **земля (GND)**. Інакше ESP32 просідає й перезавантажується в момент вмикання.
- **Ізоляція від води.** Електроніку — в герметичний IP-бокс, подалі від крапель. Вода + плата = КЗ.
- **Захист від залипання реле.** Реле може залипнути в замкнутому стані → вода ллється безкінечно.
  Рятує таймаут у коді (п.6) + клапан NC.
- **Тестування на відрі, не на теплиці.** Перший запуск ганяй логіку й таймаути на відро,
  переконайся що реле не залипає, а тоді вже став на грядку.
- **Ручний байпас — обов'язково.** Паралельно з електроклапаном постав звичайний кран-байпас.
  Якщо електроніка померла посеред спеки — батько відкриває кран рукою і поливає як завжди.
  Система, яка при поломці лишає теплицю без води взагалі, — гірша за відсутність системи.
  Це ще й головний фактор довіри: людям легше прийняти автоматику, яку можна обійти вручну.
- **Живлення вузлів — з'ясувати до закупівлі.** Чи є 220В у кожній теплиці? Якщо так — блок
  живлення і жодних проблем. Якщо ні — сонячна панель + акум + deep sleep, але тоді вузол
  спить і **не чує команд** з бази більшість часу → архітектура зміщується до "вузол повністю
  автономний, LoRa тільки для телеметрії за розкладом". Це рішення треба ухвалити на старті.
- **Зима.** Вода в клапані/трубах замерзає → розриває. Передбачити осіннє зливання магістралі
  й клапанів (нахил труб, зливний кран у нижній точці) або зимову консервацію системи.

## 9. Дорожня карта реалізації

**Етап 1 — Автоматика на порогах (без ML, вже корисно)**
- Зібрати один вузол: ESP32 + сенсор вологості + реле + клапан.
- Локальна логіка "вологість < поріг → лий до цілі" з усіма запобіжниками.
- Тест на відрі → потім у теплиці.
- *Результат: вода сама, врожай під захистом, навіть якщо ML ніколи не буде.*

**Етап 2 — Зв'язок і телеметрія**
- Додати LoRa: вузол шле дані на базу, база логує в CSV / БД.
- База може слати команду-ціль (зворотний канал), але локальна логіка лишається фундаментом.
- Накопичення історії: сенсори + дії системи + (пізніше) зовнішній прогноз.

**Етап 3 — Масштаб**
- Кілька теплиць, кожна — автономний вузол зі своїм клапаном.
- База обслуговує всі, не блокуючись на жодній.

**Етап 4 — ML-шар (коли назбирається історія)**
- Модель на власних даних: погода (API) + сенсори + **дії системи** (полив/вікна — видимі, бо система сама їх робить).
- Прогноз локальних умов і корекція зовнішнього прогнозу під точку.
- Прогнозне керування: "не лий — завтра дощ", "відкрий вікно щоб втримати 24°".
- **Важливо:** розбивка train/test **по часу**, не випадкова (інакше витік майбутнього в минуле).

## 10. Чому дії оператора треба зробити видимими (для ML)

Наївна модель не може відділити "температура впала бо похмуро" від "температура впала бо відкрили вікно" —
це **confounding + feedback loop**. Рішення: **логувати дії як фічі.** А оскільки в цій архітектурі
**система сама керує** поливом (і згодом вікнами), вона *за визначенням* знає кожну свою дію —
дія стає видимою безкоштовно, як побічний ефект автоматизації. Автоматизація й збір даних тут — одна робота, не дві.

Це відкриває сильнішу версію: модель, яка знає ефект кожної дії, може відповідати не лише
"яка буде температура", а "**що зробити**, щоб була потрібна" — тобто перерости з прогнозу в рекомендаційне керування.

## 11. Оцінка архітектури

### Сильні сторони (що в цьому дизайні справді добре)

- **Offline-first.** Вода не залежить від радіо, бази, інтернету. Кожен рівень деградує граційно:
  впала база → вузли поливають самі; впав вузол → ручний байпас. Це найцінніша властивість дизайну.
- **Fail-safe за замовчуванням.** NC-клапан + таймаут + ліміт циклів + watchdog: кожна типова
  поломка (сенсор, реле, прошивка, живлення) має окремий запобіжник, і всі вони ведуть до "вода закрита".
- **Розділення "що" і "як".** Мозок ставить цілі, вузол виконує — класичний supervisory control.
  Масштабується на N теплиць без ускладнення жодного вузла.
- **Дані як побічний ефект.** Система логує власні дії безкоштовно, що знімає проблему
  confounding для майбутнього ML — рідкісний випадок, коли архітектура сама готує собі датасет.
- **Кожен етап цінний сам по собі.** Автополив на порогах корисний навіть якщо ML не станеться.
  Немає ставки "все або нічого".

### Слабкі місця та ризики (чесно)

| Ризик | Суть | Мітигація |
|---|---|---|
| **Сенсор — єдине джерело правди** | Вся логіка "лий до 60%" стоїть на дешевому сенсорі ґрунту. Ємнісні теж дрейфують і потребують калібрування (сухий/мокрий ґрунт — не 0/100% з коробки) | 2-3 сенсори + медіана; калібрування на місці; резервний контроль "по часу" як fallback |
| **"60% вологості" — не універсальна ціль** | Різні культури, ґрунти й глибини хочуть різного; число з голови може бути хибним | Стартові пороги питати в батька (він знає коли поливати!), калібрувати за його практикою |
| **LoRa губить пакети** | Наївний протокол → загублені команди або подвійний полив | msg_id + ACK + ідемпотентність (п.7) |
| **Одна база = єдина точка збору даних** | Впала база на тиждень — діра в датасеті для ML | Вузол буферизує останні N рапортів локально й дошле при відновленні |
| **Немає зворотного зв'язку про фактичну воду** | "Лив 90 сек" ≠ "вилив X літрів": тиск плаває, крапельниці забиваються | Ідея на виріст: імпульсний лічильник води (YF-S201, копійки) на відводі — тоді ML вчиться на літрах, а не секундах |
| **Людський фактор** | Батько може поливати вручну повз систему → знову невидимі дії, знову confounding | Байпас з датчиком потоку/геркона, або домовленість "ручний полив — тільки через кнопку на вузлі" |
| **Прошивку треба оновлювати** | Ходити з ноутом до кожної теплиці набридне швидко | ESP32 має Wi-Fi: OTA-оновлення коли вузол у зоні покриття, або оновлення через SD |

## 12. Ідеї для розвитку (за пріоритетом)

**Близькі (варто закласти одразу):**
1. **Heartbeat + алерти.** Вузол мовчить довше N хвилин → база шле сповіщення в **Telegram-бот**.
   Аварійні рапорти ("таймаут", "підозрілий сенсор") — туди ж. Це перетворює систему з "чорної
   скриньки в полі" на таку, якій можна довіряти. Telegram Bot API + твій FastAPI — годинна робота.
2. **Кнопка ручного поливу на вузлі.** Фізична кнопка "полий зараз" на боксі — батькові не треба
   ні телефон, ні база. І дія лишається видимою для логів (вирішує людський фактор частково).
3. **Лічильник води** (YF-S201, ~$3) — переводить логи з "секунд" у "літри". Дешево зараз,
   цінно для ML потім.

**Середні (після Етапу 2):**
4. **Дашборд на FastAPI + графіки.** Температура/вологість по теплицях, історія поливів,
   останні аварії. Твій рідний стек, і батько бачить теплиці з телефона.
5. **Зони поливу.** Кілька клапанів на теплицю (різні культури/грядки) — той самий вузол,
   більше каналів реле. Архітектура це вже підтримує без змін.
6. **База даних замість CSV.** SQLite вистачить надовго; структура таблиць одразу під ML
   (телеметрія, команди, рапорти, зовнішній прогноз — окремі таблиці, зв'язані по часу).

**Далекі (Етап 4+):**
7. **Вікна/вентиляція** — другий виконавчий механізм, та сама схема "ціль → локальний контур".
8. **Фертигація** — дозування добрив у полив (ще один клапан + бак). Логічне продовження.
9. **CV-шар** — камера + YOLO на стан рослин (окремий проєкт, що з'єднується з цим через спільну БД).

## Підсумок ключових рішень

| Питання | Рішення | Чому |
|---|---|---|
| LoRa чи LoRaWAN | Чиста LoRa P2P | Простота, повний контроль, двосторонність без вікон |
| Хто вирішує "коли стоп" | Вузол локально | Вода не залежить від радіо; стійкість до втрати зв'язку |
| Хто ставить ціль | База (мозок) | Централізований розум, потім ML |
| Клапан чи керування насосом | Клапан на теплицю | Немає конфлікту теплиць за насос |
| Тип клапана | 12В NC | Пропало живлення = закрито, теплицю не заллє |
| Живлення клапана | Окремий блок 12В, спільна GND | ESP32 не просідає при вмиканні |
| Захист від потопу | Таймаут + ліміт циклів + санітарка + NC + watchdog | Кожна типова поломка має свій запобіжник |
| Режим поливу | Імпульсний (лий → пауза → замір) | Вода має час всотатись; без overshoot і переливу |
| Сенсори ґрунту | Ємнісні, 2-3 на зону, медіана | Резистивні кородують; одна точка ≠ грядка |
| Надійність LoRa | msg_id + ACK + ідемпотентність | Радіо губить пакети; без цього — подвійний полив |
| Ручний байпас | Обов'язково, кран паралельно клапану | Поломка електроніки не лишає теплицю без води |
| Сповіщення | Telegram-бот з бази (heartbeat + аварії) | Довіра до системи; аварії видно одразу |
| ML — коли | Етап 4, після накопичення історії | Немає на чому вчити без даних |
